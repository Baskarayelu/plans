# Plans indexer (Envio HyperIndex)

This indexer turns Plans contract events on Monad into the data the app reads: plans, member ledgers, live balances, budget bars, the settle-up graph, the activity feed, a fresh-device rebuild, and the public traction stats. The app does not keep its own database. Everything it shows about money comes from this indexer's GraphQL API.

- Envio HyperIndex `envio@3.12.1` (the npm `latest` tag on 6 Oct 2026), TypeScript handlers, Vitest tests.
- Chains: Monad mainnet `143` and testnet `10143`. Both are native HyperSync networks, so no RPC is configured.
- Contracts: `PlansFactory`, `KeyRegistry`, `ClaimEscrow`, `PlansSend` and `FxReference` have static addresses. Every `Pot` is registered dynamically from `PlansFactory.PotCreated`.
- Entities are stored per chain (`disable_default_cross_chain: true`), so filter every query by `chainId`. Addresses are stored lowercase.

```
indexer/
├── config.yaml              chains, contracts, events (addresses come from ENVIO_* env vars)
├── schema.graphql           raw/lifecycle entities and derived/aggregated entities
├── abis/                    event ABIs (generated by scripts/sync-abis.mjs from contracts/out)
├── internal-accounts.json   demo and team accounts excluded from traction
├── src/handlers/            PlansFactory.ts · Pot.ts · KeyRegistry.ts · ClaimEscrow.ts · PlansSend.ts · FxReference.ts
├── src/lib/                 domain.ts (ledger, stats, corridors, graph) · settlement.ts (pure math) · store.ts · util.ts · internal.ts
├── test/                    createTestIndexer() simulations + pure unit tests
└── queries/                 the GraphQL queries the app uses (+ run.mjs, which checks them against a live endpoint)
```

## What HyperIndex drives in the app (Envio bounty)

| App feature | Entities |
|---|---|
| Home: my plans, my position in each | `Member` (by `account_id`) → `Pot` |
| Plan screen: balances, who owes whom, "settle up" preview | `MemberBalance`, `SettlementEdge` (recomputed on every ledger change) |
| Budget bars per category | `CategorySpend` (budget, spent, remaining) |
| Approvals inbox, disputes, rule changes | `Spend` (Pending/Approved) + `Vote`, `Dispute`, `RuleChange` |
| Spend detail with exact cost shares | `SpendShare` (replaced on dispute resolution, reduced on escrow refund) |
| Activity feed | `Activity` (one row per event, per plan and per account) |
| Fresh-device rebuild ("I already use Plans") | `Account` (key, country) → `memberships` → `Pot.meta`, `KeyWrap` |
| Public `/stats` page | `GlobalStats`, `DailyStats`, `Corridor` (internal accounts and demo plans excluded) |
| Send receipt: applied rate vs the Chainlink reference | `Send` (`fxRoundId`, `refRateE8`, `fxDiffBps`) → `FxRound` |
| Settlement FX label, "collect my payout" after settlement | `PotSettlement.fxRound`, `Payout.source` / `collectedBy`, `Pot.totalCollected` |
| Latest reference rates, CRE mode | `FxReferenceConfig.latestRound` → `FxRound` |

The schema has 34 entities and 15 enums. Of these, 8 are derived and aggregated by the handlers (`MemberBalance`, `CategorySpend`, `SettlementEdge`, `Corridor`, `PotCorridor`, `PotDaily`, `DailyStats`, `GlobalStats`), plus an audit trail, `CorridorFlow`. The schema uses `@derivedFrom` relations throughout.

## Ledger (mirrors docs/protocol.md)

For every member: `net = contributed + personalPaid − share − withdrawn`. The indexer also tracks `Pot.balance` independently from money in and out, and the tests assert invariant I1, `Σ net == balance`, after every scenario.

| Event | Indexer update |
|---|---|
| `Contributed(member, amount)` | `contributed += amount`, `balance += amount` |
| `SpendExecuted(id, amount, members, shares, claimId)` | PAY/LINK: `balance −= amount`. PERSONAL: proposer `personalPaid += amount`. Each `members[i]` gets `share += shares[i]` (exact amounts from the event), one `SpendShare` per member, and `CategorySpend.spent += amount`. |
| `DisputeResolved(id, outcome, members, shares)` | Resplit / SpenderCovers: the spend's current `SpendShare`s are removed from the ledgers and replaced by the event's exact assignment. Keep: the contract re-emits the current assignment and moves nothing, so the ledger is left alone. |
| `EscrowRefunded(spendId, amount)` | `balance += amount`. Shares are reduced the way the contract does it, with `_parts(refund, w)`: `r_i = amount·w_i/Σw` floored for i ≥ 1, and `r_0` (the first split member) gets the remainder. `w` is the current split's weights: the proposal weights, or `[1]` after SpenderCovers. After a Resplit the event's parts stand in for the weights, because the event does not carry weights. A full refund, the only kind ClaimEscrow produces, reverses the shares exactly either way. Also `CategorySpend.refunded += amount`, but `spent` and `remaining` are not reduced, because the contract does not give the budget back. |
| `Pulled(member, amount)` | `contributed += amount` (and `pulled`), `balance += amount` |
| `DebtPaid(member, amount)` | `contributed += amount` (and `debtPaid`), `debt −= amount`, `balance += amount` |
| `Payout(member, amount)` | `withdrawn += amount`, `balance −= amount`. The `Payout` row starts with `source = Automatic`. |
| `Collected(member, by, amount)` | No ledger change: `collect(member)` emits `Payout(member, amount)` immediately before it, and that Payout already moved `withdrawn`/`balance`. The handler marks that Payout (the previous log, same tx, same member and amount) `source = Collect`, `collectedBy = by`, adds `amount` to `Pot.totalCollected` (a subset of `totalPaidOut`) and writes a `Collected` activity row whose `ref` is the Payout id. |
| `DebtRecorded` / `MemberExited` / `Settled` | debt, status and settlement records. The money moves through the events above. `Settled.fxRoundId` is stored on `PotSettlement` (linked to `FxRound` when non-zero). |

### Settle-up graph (`SettlementEdge`)

The graph is recomputed after every change to any member's net, using a deterministic greedy min-cash-flow (`src/lib/settlement.ts`):

1. Debtors (net < 0) and creditors (net > 0) are each sorted by amount (largest first), then by address (ascending).
2. The largest remaining debtor pays the largest remaining creditor `min(debt, credit)`. Whichever side reaches zero moves to the next party.
3. Credit still owed after all debts are matched is owed by the pot's own balance. This becomes a `PotToMember` edge. Because `Σ net = balance`, this is the leftover money. The reverse case, a `MemberToPot` edge, only appears while a transaction's events are half applied.
4. Edges that no longer exist are deleted. `Pot.edgeIds` lists the current set.

Guarantees, which the tests check on 2,000 random pots and after every integration scenario:
- Σ edges out of debtors equals Σ debts, and Σ edges into creditors equals Σ credits.
- Every member is on one side only.
- There are at most (#debtors + #creditors − 1) member-to-member edges.
- The output is the same whatever the input order.

`MemberBalance` holds `net`, `owes`, `owedByMembers`, `owedByPot` and `settledUp` for each member.

## Corridors (`Corridor`, `PotCorridor`, `CorridorFlow`)

A corridor is an ordered country pair `FROM-TO` (ISO 3166-1 alpha-2), for example `GB-IN`. Flows whose country is unknown on either side are not attributed. Domestic pairs (`GB-GB`) are stored with `isCrossBorder = false`. Each attributed flow also gets a `CorridorFlow` row with its source.

| Source | From country | To country | Amount |
|---|---|---|---|
| `Send` (`PlansSend.Sent`) | `fromCountry` | `toCountry` | `amount` |
| `SendLinkClaim` (send-by-link: `ClaimCreated` + `Claimed`) | `ClaimCreated.fromCountry` | `Claimed.toCountry` | claim amount |
| `PotLinkClaim` (a pot LINK spend claimed) | `ClaimCreated.fromCountry`, or the spend proposer's member country if that is zero | `Claimed.toCountry` | claim amount |
| `SettlementPull` (`Pulled`) | debtor's member country | each creditor's member country | the pull is split across the debtor's current `MemberToMember` edges, taken before the pull is applied (largest edge first) |
| `DebtPayment` (`DebtPaid`) | debtor's member country | each creditor's member country | same split as for pulls |

A `Payout` is not attributed by itself, because the pot holds pooled money. The cross-member part of a settlement is the debtor's money reaching creditors, so it is counted once, on the pull or debt payment side.

`volume`/`count` are traction figures and exclude internal and demo flows. `volumeAll`/`countAll` include everything. Pot flows also go into `PotCorridor`, so they can be retracted if the plan turns demo.

## FX reference (`FxRound`, `FxReferenceConfig`)

`FxReference` is a Chainlink CRE receiver. It stores reference FX rates in numbered rounds and never moves funds; FX never changes an AUSD amount.

| Event | Indexer update |
|---|---|
| `RoundWritten(roundId, scheduledTime, rateDate, sourceMask, usdPerUnitE8[], sourceMasks[])` | One `FxRound` (id = `roundId` in decimal, per chain like every entity). Rates are USD per 1 unit, 8 decimals, in the fixed order GBP, EUR, INR, NGN, JPY, CHF, AED, SGD: the raw arrays plus `rateGBP`…`rateSGD` and `maskGBP`…`maskSGD`. A rate of 0 (mask 0) means the currency is absent from that round. `writtenAt` is the block time, `scheduledTime` the CRE cron time as emitted. `FxReferenceConfig.latestRound` moves to it. |
| `SimulationModeSet` / `ProductionModeSet` / `MaxMoveSet` / `OwnershipTransferStarted` / `OwnershipTransferred` | `FxReferenceConfig` (id = contract address): `mode`, `forwarder`, `simTransmitter` (simulation only), `workflowId`/`workflowOwner` (production only), `maxMoveBps`, `owner`, `pendingOwner`. The constructor emits the ownership, simulation and max-move events, so the row exists from the deploy block. |
| `PlansSend.Sent(…, fxRoundId, refRateE8, fxDiffBps)` | `Send.fxRoundId`, `refRateE8` (the round's toCurrency per 1 fromCurrency, 8 dp, floored) and `fxDiffBps` (signed: `(applied − ref)·10000/ref`, truncated toward zero), all as emitted. `Send.fxRound` links to the round when `fxRoundId ≠ 0`; all three are 0 when the send cited no round. |
| `Pot.Settled(…, fxRoundId)` | `PotSettlement.fxRoundId` and `fxRound` (when non-zero). It is a display label only: the round that was fresh (≤ 6 h) at settle time. |

## Internal accounts and demo plans

`internal-accounts.json` lists internal accounts. It starts empty.

```json
{ "accounts": [
  { "address": "0x…", "kind": "demo", "label": "Ben (demo)" },
  { "address": "0x…", "kind": "team", "label": "team test phone" }
] }
```

- **Internal account:** any listed address (`Account.isInternal`, `internalKind` Demo or Team).
- **Demo plan:** the creator is internal (any kind), or any member is a `demo` account.
- **Retraction:** a plan can turn demo after creation, when a demo member joins later. Everything it had contributed is then retracted: plans created, funded plans, every per-day row, histograms, corridors, its members' user status and their time-to-first-funded-action samples (`applyPotToStats(pot, −1)`).
- **Changing the list:** the list is applied while indexing. After editing it, commit and redeploy, which reindexes from scratch.
- **Tests:** they use `test/fixtures/internal-accounts.json` via `ENVIO_INTERNAL_ACCOUNTS_FILE`.

## Metric definitions (GlobalStats, DailyStats)

All metrics are per chain and exclude internal accounts and demo plans. A plan counts once `PotCreated` is seen and while it is not demo (`Pot.countedInStats`).

| Metric | Field | Definition |
|---|---|---|
| Users | `users` | Non-internal accounts that joined at least one counted plan (`MemberJoined`), or sent or claimed at least one non-internal send (`Sent` sender, send-by-link creator, send-by-link claimer). A send is internal if either side is internal. `DailyStats.newUsers` counts users on the day they first qualified. |
| Accounts | `accounts` | Distinct non-internal addresses with a `KeyRegistered` event. This is the "Accounts" row in docs/traction.md. |
| Plans created | `potsCreated` | `PotCreated` from the factory, counted plans only |
| Funded plans | `fundedPots` | Counted plans with at least one `Contributed` (pulls and debt payments do not count) |
| Members per plan | `membersPerPotHistogram`, `medianMembersPerPot` | Histogram index i is the number of counted plans with i active members, which is the current count while a plan is open and the count at the end once settled. The median averages the two middle values when the count is even. |
| Countries per plan | `countriesPerPotHistogram`, `medianCountriesPerPot` | Distinct non-empty country codes among all members who ever joined the plan |
| Time to first funded action | `Account.timeToFirstFundedAction`, `ttffaHistogram`, `medianTtffa{Lower,Upper}Seconds` | For each account: seconds from its first `MemberJoined` (in any plan) to its first `Contributed`, `Sent` or `Claimed` at or after that join. A sample counts if the account is non-internal and its first join was in a counted plan. Histogram buckets start at `ttffaBucketsSeconds` (0, 10 s, 30 s, 1 m, 2 m, 5 m, 15 m, 1 h, 6 h, 1 d, 3 d, 7 d). For the exact median, query `Account(where: {ttffaCounted: {_eq: true}}, order_by: {timeToFirstFundedAction: asc})`. |
| Spends | `spends`, `spendVolume` | `SpendExecuted` events (all kinds) and their amounts |
| Approvals | `approvals` | `Voted` events with `approve = true`. The proposer's implied approval is not counted. |
| Settlements | `settlements` | `Settled` events |
| Settled volume | `settledVolume` | Σ `Settled.paidOut`, which is the payouts made in the settle transaction (later `collect` payouts are not included; see `Pot.totalCollected`) |
| Sends | `sends`, `sendVolume` | Non-internal `Sent` events |
| Claims | `claims`, `claimVolume` | Non-internal send-by-link claims (`Claimed` where the source is not a pot) |
| Cross-border volume | `crossBorderVolume`, `crossBorderCount` | Σ counted corridor flows where the two country codes differ. Per pair: `Corridor.volume`. |
| Context | `allPots`, `demoPots`, `allAccounts`, `internalAccounts` | Unfiltered totals |

### Differences from docs/traction.md (flagged, not edited)

1. **Users vs Accounts.** traction.md defines "Accounts" as addresses with `KeyRegistered`. The `users` metric, defined above, is a different and stricter measure. Both are provided. traction.md and the stats page should say which one is the headline.
2. **Exclusions.** traction.md does not say that internal accounts and demo plans are excluded. The indexer excludes them from every metric.
3. **Approvals.** traction.md says "`Approved` events", but no such event exists. `SpendApproved` means "threshold met but not executable yet". The indexer counts `Voted(approve = true)`.
4. **Members per plan "at the plan's end".** Plans that are still open contribute their current active count. Once a plan is settled, its count is final.
5. **Cross-border volume.** traction.md describes sender and receiver countries. The indexer also counts pot-mediated flows (LINK claims, settlement pulls, debt payments), attributed as described under Corridors.
6. **Time to first funded action.** This is measured per account, from the first join in any plan, and excludes accounts whose first join was in a demo plan.

## Run locally

Prerequisites: Node ≥ 22, pnpm, Docker (or Colima/Podman), and an Envio API token from https://envio.dev/app/api-tokens for HyperSync.

```bash
cd indexer
pnpm install
pnpm codegen          # generates .envio/types.d.ts from config.yaml + schema.graphql
pnpm typecheck
pnpm test             # 26 tests, no network, no Docker
cp .env.example .env  # set ENVIO_API_TOKEN and, once deployed, the contract addresses
pnpm dev              # Postgres + Hasura in Docker, indexer, GraphQL at http://localhost:8080/v1/graphql (password: testing)
node queries/run.mjs  # checks every app query against the running endpoint
```

- With Colima, set `export DOCKER_HOST=unix://$HOME/.colima/default/docker.sock`.
- After any schema change that is incompatible with the existing data, run `npx envio dev -r`.
- `npx envio stop` removes the local containers and database.
- When the contract events change, run `forge build` in `contracts/`, then `pnpm sync-abis` and `pnpm codegen`.

## Deploy on Envio Cloud (hosted service)

1. Fill in the addresses. Set these as env vars (all must use the `ENVIO_` prefix):
   - `ENVIO_MAINNET_FACTORY_ADDRESS`, `ENVIO_MAINNET_KEY_REGISTRY_ADDRESS`, `ENVIO_MAINNET_CLAIM_ESCROW_ADDRESS`, `ENVIO_MAINNET_SEND_ADDRESS`, `ENVIO_MAINNET_FX_REFERENCE_ADDRESS`, `ENVIO_MAINNET_START_BLOCK`
   - the same six with `TESTNET` in place of `MAINNET` (`fxReference` is in `contracts/deployments/<chainId>.json`)

   Unset addresses fall back to inert placeholders, so one chain can be deployed before the other. The start block may stay `0`: HyperSync jumps to the first event, but the deployment block is faster and explicit.
2. In https://envio.dev/app, add an indexer from the GitHub repo:
   - root directory: `indexer`
   - config file: `config.yaml`
   - branch: `main`

   Then set the env vars above under the indexer's settings. The CLI does the same: `npx envio-cloud indexer add --name plans --repo <org/repo>`, then `npx envio-cloud indexer env set …`.
3. Push to the deployment branch to deploy. Watch it with `npx envio-cloud deployment status plans <commit> --watch-till-synced`. Get the GraphQL URL with `npx envio-cloud deployment endpoint plans <commit>`, then promote the deployment.
4. Point the app and the stats page at that endpoint, and run `node queries/run.mjs <endpoint>`.
5. Before inviting real users, fill `internal-accounts.json` with the demo members (Ben, Asha, Maya) and the team test accounts, commit and redeploy.

## GraphQL queries the app uses

The full set is in `queries/`. `node queries/run.mjs` validated all of them against a live local Hasura on 6 Oct 2026; `queries/fx.graphql` and the `settlements`/`payouts`/`totalCollected` additions to `planDetail.graphql` were added on 7 Oct 2026 for the FX and `collect` changes. Pass addresses in lowercase.

**Plans for an address** (`queries/myPlans.graphql`)

```graphql
query MyPlans($account: String!, $chainId: Int!) {
  Member(where: { account_id: { _eq: $account }, chainId: { _eq: $chainId } }, order_by: { joinedAt: desc }) {
    id status net contributed share debt
    pot { id meta inviteKeyWrap status startTime endTime balance memberCount activeMemberCount countries
          frozenUntil isDemo lastActivityAt spends(where: { status: { _in: ["Pending", "Approved"] } }) { id } }
  }
  Account(where: { id: { _eq: $account }, chainId: { _eq: $chainId } }) {
    id key country isUser keyWraps(order_by: { timestamp: desc }) { pot_id by_id wrap timestamp }   # fresh-device rebuild
  }
}
```

**Plan detail: members, balances, category spend, settle-up edges** (`queries/planDetail.graphql`, abridged)

```graphql
query PlanDetail($pot: String!, $chainId: Int!) {
  Pot(where: { id: { _eq: $pot }, chainId: { _eq: $chainId } }) {
    id meta status startTime endTime balance frozenUntil ackEpoch acksInEpoch instantMax oneApprovalMax highTier
    members(order_by: { memberIndex: asc }) { address country status contributed personalPaid share withdrawn net debt }
    balances(order_by: { net: desc }) { account_id net owes owedByMembers owedByPot settledUp }
    categorySpends(order_by: { category: asc }) { category name budget spent refunded remaining spendCount }
    settlementEdges(order_by: { amount: desc }) { kind from_id to_id amount fromCountry toCountry }
    spends(where: { status: { _in: ["Pending", "Approved"] } }) { id kind amount approvals approvalsRequired expiresAt votes { account_id approve } }
    disputes(where: { status: { _eq: "Open" } }) { id spend_id reason votesSpenderCovers votesKeep }
  }
}
```

**Activity feed** (`queries/activity.graphql`)

```graphql
query PlanActivity($pot: String!, $chainId: Int!, $limit: Int = 50, $offset: Int = 0) {
  Activity(where: { pot_id: { _eq: $pot }, chainId: { _eq: $chainId } },
           order_by: [{ timestamp: desc }, { id: desc }], limit: $limit, offset: $offset) {
    id kind account_id counterparty amount ref timestamp txHash
  }
}
```

**FX reference** (`queries/fx.graphql`): `LatestFxRound` (the config row with its `latestRound` and every per-currency rate and mask) and `AccountSendReceipts` (an account's sends with `fxRoundId`, `refRateE8`, `fxDiffBps` and the linked `fxRound`).

**Global stats** (`queries/stats.graphql`, abridged)

```graphql
query Stats($chainId: Int!) {
  GlobalStats(where: { id: { _eq: "global" }, chainId: { _eq: $chainId } }) {
    users accounts potsCreated fundedPots medianMembersPerPot medianCountriesPerPot
    ttffaSamples medianTtffaLowerSeconds medianTtffaUpperSeconds
    spends approvals settlements settledVolume crossBorderVolume updatedAt
  }
  DailyStats(where: { chainId: { _eq: $chainId } }, order_by: { day: asc }) { date newUsers potsCreated spends settledVolume crossBorderVolume }
  Corridor(where: { chainId: { _eq: $chainId }, isCrossBorder: { _eq: true }, count: { _gt: 0 } }, order_by: { volume: desc }) {
    fromCountry toCountry volume count
  }
}
```

## Assumptions about contract events

The handlers rely on the following. Items marked ✔ were checked against the in-progress `contracts/src` on 6 Oct 2026, and all of them need to stay true.

- ✔ `RulesSet` is emitted on `initialize` (version 0) and on every applied rule change. It is the source of the category budgets.
- ✔ A deposit inside `join` or `createPot` emits `Contributed`.
- ✔ `Pulled` and `DebtPaid` are not also emitted as `Contributed`, because the indexer adds them to `contributed` itself.
- ✔ `SpendProposed` is emitted before `SpendExecuted`, including for instant spends. For LINK spends, `ClaimCreated` (with `fromCountry = 0`) comes before `SpendExecuted`.
- ✔ Exit, settlement, debt distribution and post-settlement refund distribution all emit `Payout`. Exit pulls emit `Pulled`.
- ✔ `payDebt` emits `DebtPaid` before its `Payout`s. Only the corridor split depends on this order; the ledger does not.
- ✔ `collect(member)` emits `Payout(member, amount)` and then `Collected(member, by, amount)` with no external call in between, so the Payout is the log right before Collected (checked against `contracts/src/Pot.sol` on 7 Oct 2026). A Collected without that Payout is logged as an error and changes nothing.
- ✔ `Settled` carries `fxRoundId` (0 = no fresh round) and `Sent` carries `fxRoundId`, `refRateE8`, `fxDiffBps`; event topic0s were checked against `contracts/out` on 7 Oct 2026.
- ✔ `PotCreated` is emitted before `initialize`. The reverse order is also handled and tested: Envio indexes same-block events of newly registered contracts, and the indexer creates stub rows.

## Naming note

The raw settlement record is called `PotSettlement`, not `Settlement`. Hasura's Relay schema names `Settlement_connection.edges` as type `SettlementEdge`, which collided with the `SettlementEdge` entity and broke table tracking. A local run surfaced this.
